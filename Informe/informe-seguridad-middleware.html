1. Objetivo

Implementar una tubería de middlewares inspirada en PSR-15 para centralizar autenticación, validación de fingerprint, autorización RBAC y cabeceras de seguridad. La solución evita que una petición no autorizada llegue al controlador y emplea contratos fuertemente tipados.

2. Arquitectura implementada

La petición sigue el siguiente flujo:

Petición HTTP
    -> ServerRequest
    -> MiddlewareDispatcher
       -> AuthenticationMiddleware
       -> AuthorizationRBACMiddleware
    -> ControllerRequestHandler
    -> Controlador MVC
    -> Response HTTP

Los componentes se encuentran en Libraries/Core/Http, App/Http/Middleware y App/Repositories. La integración general se realiza desde index.php.

5. Cuestionario técnico

Pregunta de evidencia 1

¿Cuál es la principal ventaja de utilizar interfaces fuertemente tipadas?

Las interfaces establecen un contrato verificable: el middleware sabe que el handler posee el método handle(), recibe un ServerRequestInterface y devuelve un ResponseInterface. Esto permite detectar incompatibilidades tempranamente, facilita el autocompletado y evita la ambigüedad de un callable genérico.

Pregunta de evidencia 2

¿Por qué se utiliza array_reverse() antes de array_reduce()?

La reducción construye la tubería desde la función final hacia afuera. Al invertir la colección, el primer middleware registrado queda como capa exterior: se ejecuta primero al entrar y último al regresar la respuesta. Así se conserva el orden esperado de la estructura de cebolla.

Pregunta de evidencia 3

¿Cómo mitiga session_regenerate_id(true) la fijación de sesión?

Después de autenticar al usuario se genera un identificador nuevo y se elimina el anterior. Si un atacante había impuesto o conocido previamente el ID de sesión de la víctima, ese identificador deja de representar la sesión autenticada y ya no puede reutilizarse para ingresar.

Pregunta de evidencia 4

¿Qué significa el cortocircuito y cómo protege al controlador?

Significa devolver una respuesta desde el middleware sin llamar a $handler->handle($request). Cuando RBAC deniega el permiso, retorna HTTP 403; por ello el controlador no se instancia ni ejecuta acciones de consulta, modificación o eliminación inseguras.

Pregunta de evidencia 5

¿Qué función cumple nosniff?

X-Content-Type-Options: nosniff ordena al navegador respetar el tipo MIME declarado por el servidor. Evita que archivos servidos como texto, imágenes u otros tipos sean reinterpretados como JavaScript o CSS, reduciendo ataques XSS basados en confusión de MIME.

7. Conclusiones

La seguridad transversal quedó centralizada en una tubería tipada. La autenticación se ejecuta antes que RBAC, el fingerprint vincula la sesión al entorno del usuario y las respuestas de rechazo impiden alcanzar el controlador. La petición se maneja de forma inmutable y el acceso a la sesión nativa se encuentra encapsulado mediante SessionInterface.
